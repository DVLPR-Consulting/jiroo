# Team-size performance profile — October 2026 (JIR-41)

Measurement of application **7915ba9** (production build, no application changes), using seed **2863e8a**. [JIR-41](https://linear.app/dvlpr/issue/JIR-41). Owner-approved target on 22 October 2026: a few backlogs, up to 20,000 items, 50 members and about ten connected users. This is a local baseline, not a production capacity guarantee.

## Environment and dataset

- Apple M5 Max, 18 CPU cores, 64 GB RAM; macOS 27.0.1 (26A434).
- Docker Desktop engine 29.6.2, ARM64 Linux VM: 18 CPUs and 8,319,213,568 bytes of available memory (~7.75 GiB).
- Node 24.18.1; Corepack pnpm 10.34.5; Next.js 16.3.8 / React 19.2.4; node-postgres 8.21.0; Drizzle ORM 0.45.2.
- PostgreSQL 17.11 (Debian 17.11-1.pgdg13+2), `jiroo-db-local`, loopback port 5434. `shared_buffers=128MB`, `work_mem=4MB`, `max_connections=100`, JIT on. Default application pool (max ten connections), plus the realtime listener. No PostgreSQL tuning or application changes.
- Standalone built with `corepack pnpm build`; served by Node from `.next/standalone/server.js` on 127.0.0.1:3441, with copied `public` and `.next/static` assets. The auth secret and synthetic passwords existed only in process memory. Runtime used the JIR-114 least-privilege grant script, not the migration superuser.
- Fresh database with 5 equally sized backlogs (4,000 items each): 100 components, 500 epics, 14,000 tasks and 5,400 subtasks. Unique global ranks per backlog, parent-first self-inclusive ltree paths, sequence-generated keys; actual parent/path/depth consistency checked after seeding.
- Exactly 50 synthetic accounts, all members of all five backlogs: one platform administrator and 49 contributors. The ten measured clients were contributors, each enrolled in TOTP using the public HTTP auth endpoints.
- 15 sprints: two completed (100 participants each) and one active (200 participants) per backlog; ten immutable completion snapshots. Historical participants start unfinished and complete via the services, including estimate changes; active sprints also contain status/estimate events. Planned dates are historical; lifecycle/audit timestamps are the real seed execution time, not fabricated historic edits.
- 15 releases (five published), 100 labels / 8,000 assignments, 2,000 acyclic `blocks` links, 11,200 comments, and 34,680 activity rows before measurement. Descriptions and comments are synthetic French text.
- After probes and load: 20,108 items and 1,150 sprint events. Newly created load items explain the difference from the 20,000-item starting profile.
- Only uniquely named disposable databases and runtime roles were created. Cleanup checked the final database absent: `true`. No Neon, port 5433, environment files or shared-container restarts.

## Method and limits

The retained run started at **2026-10-22T10:11:55.611Z**. Ten closed-loop HTTP clients ran concurrently for **183.74 seconds**, with 300 ms think time after each operation, rotating evenly through twelve operations and the five backlogs. There were **1,238 successful measured requests**, **0 recorded errors**, about **6.74 requests/second**. Authentication/enrolment and warm-up are excluded.

Read requests fetch full HTML views or the panel JSON. Actions use the actual build's Server Action IDs and the router-state headers captured from a real Chromium pointer drag on the active Board. The drag changed the target column and remained there after reloading. Concurrent mutations replay those real action requests through the public HTTP boundary, with distinct writer items per client. Creation, status and movement results must return `ok: true`; panel responses must contain detail. The large action responses include Board RSC refresh data, rather than timing a service function alone. Concurrent load does not time browser painting or hydration, and it does not repeatedly drive ten visible browsers.

**HTTP full-response time** below is start-to-body-complete on the local client, including transport, Node scheduling, SQL and serialization; it is not a pure CPU timer. **TTFB** is header arrival and can precede the streamed content. The full-response p95 is used for the indicative 500 ms page / 300 ms action checks; TTFB alone would hide streaming costs. Read-only search is also assessed at 300 ms. Panel uses 500 ms.

**SQL accounting:** one warm-up followed by three isolated requests per operation, without browser background activity or SSE streams. Counts observe PostgreSQL simple `Query` and extended `Execute` messages in a loopback TCP observer forwarding exclusively to this disposable database on 5434. Parse/Bind are not counted as extra executions. Explicit transaction control is included. The observer retains first bind values only in memory for exact representative EXPLAIN calls. No pool/library/application code was patched. Counts belong to these serial probes, not individual requests during concurrent load.

`pg_stat_statements` was available but not preloaded. No shared PostgreSQL restart was performed. Instead, `log_min_duration_statement=0` and parameter logging disabled were set **only for the disposable runtime role in its database**. Execution durations below come from PostgreSQL's `execute` / simple `statement` log records, filtered by that database's backend PIDs. Parse/Bind durations are excluded. 80,893 SQL execution records were retained; the wire observer saw 82,139 executions across setup/probes/load. These totals have different windows (authentication and listener setup are excluded from the log window), and are not compared as if identical.

The observer, full SQL logging, local Docker networking and same-host load client add overhead. This is one warm-cache local run on powerful hardware; there is no cold-cache, WAN, sustained soak, independent host or CPU isolation claim. Other Docker projects were not stopped. Percentiles are nearest-rank and are not confidence intervals. Earlier harness attempts were discarded; an earlier complete HTTP run could not retain its SQL logs because the collector buffered too much data. The retained run streams logs and checkpoints HTTP samples before SQL analysis.

## Realtime and Node memory

All ten authenticated `/api/realtime?backlog=KEY` streams reached `ready` before the workload and remained open during the writes (two subscribers per backlog). There were **412 correlated deliveries** for status/Board mutations, distributed across streams as `[40, 40, 40, 44, 42, 40, 40, 40, 44, 42]`. Request-start-to-event arrival: p50 **712.0 ms**, p95 **2,762.0 ms**, p99 **3,117.0 ms**. A delivery is counted once per item mutation and subscriber; self events are included. Creation events were not used in this latency calculation because their item IDs are unknown before the response. This measures perceived propagation from mutation request start, including authorization and commit, **not** isolated NOTIFY transport time or browser refresh latency. The two expected subscribers per changed backlog, rather than ten cross-backlog deliveries, are the correct fan-out.

Node server RSS sampled once per second (183 samples): minimum **756.4 MiB**, median **1035.6 MiB**, maximum **1191.2 MiB**. This excludes PostgreSQL, Chromium, the wire observer and load-generator processes. A three-minute RSS trace cannot establish absence of a memory leak.

## Bottlenecks and proposed follow-up

All seven page routes and the panel miss the indicative 500 ms full-response p95; all three mutations miss 300 ms, as does the read-only search action. This holds for this combined warm-cache profile; it is not a statement about every request (for example, My items has a 162 ms p50). A single SQL maximum cannot explain a page percentile on its own.

1. **Highest impact: unbounded view data and large streamed render output.** Median HTML is 26.28 MiB for List, 14.76 MiB for Backlog and 14.24 MiB for Tree; their full-response p95s are 3,501 / 2,524 / 2,389 ms. The general item query returns 4,024 complete rows, including descriptions, while the parent-choice query returns 2,944 entries. Even the item-panel API returns a median 1.22 MiB because it loads the backlog for choices. These volumes are measured; the exact share of SQL, React serialization, compression, transfer and allocation needs a CPU/response profile. **Propose server-side windows/pagination and small projections, lazy-loaded creation/parent choices, and explicit item/ancestor loading for the panel.** Client-only virtualization would not remove the data fetch and transfer by itself. Preserve hierarchy context, filters and all RBAC predicates.
2. **High impact: mutation-triggered Board reload and repeated request work.** Create/status/move each return a median 1.36 MiB and execute 129/112/113 SQL statements in isolated probes, with full-response p95s 2,881/3,209/2,410 ms. These are whole user-facing action responses, not DB writes alone. Normal item views already cost 56–58 statements; Reports costs 63. **Propose profiling the action render path, returning a minimal authorized mutation result and applying a targeted optimistic patch, then reloading only affected view data.** Batch repeated permission/principal reads or memoize them only within a request, keyed by actor and scope; evaluate request-local reuse of release/sprint summaries. This experiment does not prove an item-by-item N+1: high fixed query counts must not be labelled N+1 without varying cardinality.
3. **High impact symptom: Node scheduling/memory and realtime under rendering load.** Server RSS grows from 756.4 MiB minimum to 1,191.2 MiB maximum (median 1,035.6 MiB). Search, with only four SQL statements and a ~38 ms maximum search query, still has a 2,231 ms HTTP p95. The two subscribers expected for every status/move mutation receive all 412 correlated deliveries, but request-start-to-event p95 is 2,762 ms. **Propose a repeat with Node CPU/event-loop/GC profiling after reducing payloads, followed by a longer RSS soak.** Do not infer a memory leak or a pure LISTEN/NOTIFY bottleneck from this run; database commit time, event-loop scheduling and listener delivery are combined in the SSE measure. No realtime rewrite is justified yet.
4. **Secondary SQL work: targeted indexing and aggregates, after payload fixes.** The broad `dossier` search plan sorts matching rows using an external merge and has a 28.696 ms serial EXPLAIN, with temporary blocks. Compare a bounded/top-N FTS query shape with the key-prefix branch separated, keeping access checks; do not assume another GIN index will solve the OR/ranking shape. The per-assignee count scans 20,108 rows and keeps 419: test a partial `(assignee_id, backlog_id)` index for live items. Item-list, parent-option and version-summary plans scan items by backlog and sort; inspect existing indexes and compare a live-items `(backlog_id, depth, rank COLLATE "C", key)` candidate against write overhead and the pagination query shape. Release summary variants repeatedly aggregate the same 1,100 version links (5.5–6.1 ms serial); evaluate request-local aggregate reuse rather than a cross-user shared cache. The 60.505 ms backlog `FOR UPDATE` outlier replays in 0.031 ms without concurrency: measure lock waits before proposing lock changes. `COMMIT` also reached 12.250 ms; it has no legal EXPLAIN form. None of these observations supports adding indexes blindly.

Recommended order: reduce List/Backlog/Tree and panel data volume, then cut action refresh and repeated request work; repeat this exact workload before tuning indexes or changing realtime delivery. Keep this branch measurement-only. No implementation, migration, cache, index or application dependency was changed.
